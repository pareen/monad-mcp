monad-mcp — implementation notes

Spec: build a Monad MCP server with Privy as the wallet provider. Captured during the initial build session.

1. Design decisions

decisionPrivy @privy-io/node instead of the deprecated @privy-io/server-auth

npm install warned that @privy-io/server-auth is deprecated in favor of @privy-io/node. Swapped immediately. The new SDK exposes services via client.wallets().ethereum().sendTransaction(walletId, ...) rather than the old client.ethereum().sendTransaction shape. Adjusted PrivyAuthBridge.sendTransaction accordingly.

decisionStatic SPKI key for JWT verification, JWKS fallback

Privy's verifyAccessToken accepts either a PEM-encoded ES256 public key (fastest, no network call) or a JWKS getter. The SDK ships createPrivyAppJWKS but doesn't re-export it from the package root — and the package's "exports" map blocks deep imports. I use jose.createRemoteJWKSet directly as the fallback when PRIVY_VERIFICATION_KEY is unset. Users get the key from the Privy dashboard.

decisionStateless Streamable HTTP transport

Each POST /mcp request creates its own logical session; auth comes from the bearer token each time. Avoids session-store complexity. If we later use the experimental tool-tasks API for long-running tools, we'd flip to stateful (with sessionIdGenerator set).

decisionServer-side sendTransaction for the approval submit path

Two ways to wire approval signing: (a) browser-first via Privy's web SDK in the approval page (key stays in browser session), or (b) server-side via Privy's sendTransaction after we verify the bearer. I picked (b) for v1 — no Privy web SDK bundle to ship, no need for a frontend build step. The price is one more network hop and slightly broader trust in our server. Phase 2 swap to (a) is non-breaking — same approval URL.

decisionSplit runTool from registerTool

Initial design had a single registerTool that called the MCP SDK's mcp.registerTool with a wrapped handler. To unit-test the wrapper logic (auth gating, network resolution, zod validation, error formatting) without spinning up a transport, I factored the wrapper into a plain async function runTool(def, args, server, authInfo). registerTool is now a 3-line shim. Tests call runTool directly. Net win for test surface area.

decisionPlugins as static imports, not dynamic discovery

One alternative is a markdown-spec approach to plugins. For a TypeScript-first server, static imports give better type safety, simpler bundling, and trivial registration. If we ever want third parties to ship plugins as separate npm packages, the SkillPlugin interface is already designed for it.

decisionUniswap addresses are env-driven, default to null

I don't have verified Uniswap v3 contract addresses for Monad in this build session. Rather than ship guessed addresses that could route funds to the wrong place, the plugin reads addresses from UNISWAP_*_QUOTER_V2 and UNISWAP_*_SWAP_ROUTER_02 env vars. If unset, write tools fail loud with a configuration error; read tools return a clear "not configured" message.

2. Deviations from the spec

deviationget_transaction_history only returns ERC-20 Transfer events

Spec said "view transaction history." Without a stable Monad block-explorer API I scoped this to ERC-20 Transfer event logs over a bounded block range (default 5k blocks). The response always includes an explorer URL for the authoritative full history. To upgrade later: integrate Monad's explorer API or use Envio/Goldsky-style indexed data.

deviationApproval page does not embed Privy web SDK (resolved 2026-06-04 — see §8b)

The HTML page renders the tx summary, asset diff, and approve/reject buttons. On approve, it POSTs to the server, which does the signing via Privy server SDK. The original architecture sketch described a browser-side Privy web SDK login + sign. This "Phase 2" is now done — the page signs client-side by default (§8b); the server-submit path remains only for grant activations. As predicted, the public surface (URL contract) didn't change.

deviationOAuth 2.1 metadata advertises Privy as the AS

The protected-resource metadata document points clients at https://auth.privy.io rather than running our own AS. Aligned with how MCP OAuth 2.1 is meant to compose with existing identity providers.

3. Tradeoffs considered

tradeoffWalletConnect vs. embedded wallet

Earlier discussion: should the agent talk to the user's existing wallet (MetaMask/Rabby via WalletConnect) or to a Privy embedded wallet? Picked embedded wallet for the smoothest UX — one-click approval URL, no separate wallet install required, hosted approval page handles signing inline. WalletConnect could be added as a separate auth strategy if needed.

tradeoffMemory store vs. Postgres for stored requests

Picked in-memory for v1 — single-process dev ergonomics. The RequestStore interface is the swap-in point. Production multi-replica deployment will need Postgres (or Redis); the public tool surface doesn't change.

tradeoffAuto-expire on read vs. background sweep

Memory store expires requests lazily on get(). Fine for memory pressure in dev. Production should add a background sweep that calls markExpired to clean up the store and emit analytics events.

tradeoffQuote sweep on every swap

The Uniswap swap tool re-sweeps all fee tiers if fee isn't passed. That's 4 quoter calls per swap. Faster: keep a tier cache per token pair (TTL ~30s). Skipped for v1 — premature optimization on a low-call-rate path.

4. Open questions

openCanonical Uniswap addresses on Monad

Need to verify the QuoterV2 + SwapRouter02 addresses against the Uniswap deployments page. The plugin won't function until these are supplied via env. I left ENV_KEYS scaffold ready and documented the requirement in README + ARCHITECTURE.

openWallet creation flow

Privy users may not have an Ethereum embedded wallet yet (only social login). The current code throws WalletNotFoundError in that case. Consider exposing a create_wallet tool (or auto-create on first auth) that calls client.users()._get → client.wallets().create(). Need to check whether the agent should drive that or the approval page handles it on first visit.

openPrivy caip2 string format

I'm passing "eip155:143" / "eip155:10143" to sendTransaction. The Privy node SDK's request type isn't fully reified for our use case — I cast at the boundary. Worth a quick e2e test on testnet to confirm acceptance before mainnet.

openStreamable HTTP + session ID

Stateless mode currently means every POST /mcp is independent. Some clients may expect a session-id header. Investigate compatibility with Claude Web specifically; we may need to flip to stateful with a JWT-derived session id.

openBlock explorer URL for testnet

I used https://testnet.monadexplorer.com based on the research pass. Verify this resolves; if not, fall back to https://testnet-explorer.monad.xyz or whatever the canonical URL is.

5. Phase 3 — making it actually work (this session)

Validation pass against live Monad testnet uncovered two Privy behaviors that don't match the surface impressions of the SDK. Both blocked the first end-to-end attempt; both are now fixed and pinned by an integration test.

decisioncaip2 lives at the top level of the wallets RPC body, not inside params

The SDK's EthereumSendTransactionRpcInput declares caip2: AppsAPI.Caip2 as a top-level field alongside method and params. My first implementation followed the more intuitive shape — params: { transaction, caip2 } — and Privy rejected with the confusing dual error "caip2 is required" + "params: Unrecognized key(s) in object: 'caip2'". Once moved up one level, the request validated. Pinned in the integration test so the shape can't drift.

decisionEmbedded wallets need an additional_signer attached at creation; there's no retrofit

Privy's user-created embedded wallets (from users().create({wallets: [...]}) without further config) are user-owned. The server has no authorization to sign on them — sendTransaction returns "No valid authorization keys or user signing keys available". The fix: register a P-256 key quorum once, attach it as an additional_signer on the wallet at creation time. Retrofit is not possible — calling wallets()._update to add a signer requires the very signer authorization we're trying to install. The first test wallet (and its 5 MON) became unreachable as a result; we minted a fresh one with the quorum attached and proceeded.

decisionOne-time bootstrap script for the auth keypair

npm run bootstrap:auth-key generates a P-256 keypair, registers the public key as a Privy key quorum, and prints the env vars to paste into .env. Idempotent — refuses to re-run if the env is already populated. Crucially, the script prints the secrets before any subsequent step that might fail, so a failure halfway through doesn't strand the keypair.

decisionServer signing path uses authorization_context.authorization_private_keys

Every wallet operation now includes authorization_context: { authorization_private_keys: [env.PRIVY_AUTHORIZATION_PRIVATE_KEY] }. The Privy SDK signs the request with that key and includes the signature in the privy-authorization-signature header automatically. PrivyAuthBridge.hasServerSigning exposes the readiness check; PrivyAuthBridge.fromConfig reads everything from env.

decisionPin the discoveries with an integration test

Added tests/integration/transfer.integration.test.ts: runs the same flow as scripts/e2e-transfer.ts but as a vitest suite. Gated on PRIVY_* + MONAD_MCP_E2E_USER_ID + the wallet being funded — describeOrSkip pattern, so unit-test runs (npm test) are unaffected. When credentials are present, it broadcasts a real testnet tx and confirms the receipt. Run it via npm run test:integration.

tradeoffFunding cost of every "first wallet" iteration

Because we can't retrofit signers, every developer iterating on the bootstrap flow needs a fresh wallet — and a fresh trip to the faucet — for each fresh keypair. For solo dev that's fine; for a team this would warrant a shared dev key quorum so onboarding doesn't re-fund N wallets.

openRecovering stranded user-only wallets

The original test wallet (0x7970…4d77) has 5 MON we can't reach without a user JWT. Three paths to recover: (a) mint a Privy user JWT for that user via a frontend, (b) drain it manually via the dashboard if Privy exposes that, (c) just write it off. Worth confirming the policy before we ever onboard real users.

openFailure semantics of authorization_context

If the private key in .env doesn't match the key quorum attached to the wallet, Privy returns the same 401 we saw before. Need to surface that as a distinct error in PrivyAuthBridge.sendTransaction — currently it propagates as a generic AuthenticationError from the SDK.

6. Phase 4 — DeFi plugins (this session)

Built four plugins on top of the existing plugin framework: Kintsu (liquid staking), FastLane shMONAD (liquid staking), Morpho (lending), Kuru (CLOB). All write tools auto-route through the session-key grant system for free.

deviationaPriori removed — replaced by FastLane shMONAD

An earlier build shipped an aPriori liquid-staking plugin (aprMON, ERC-7540 async redemption). It was removed after aPriori was flagged as a scam — the plugin, its tests, and the aprMON canonical-token entry were deleted so portfolio/resolver tools no longer surface the token. The liquid-staking slot is now filled by FastLane shMONAD (shMON, verified vault 0x1B68626dCa36c7fE922fD2d55E4f631d962dE19c). shMONAD is a clean ERC-4626 vault with a payable native deposit and synchronous redeem — simpler than both Kintsu (batch unlock) and the old aPriori (epoch wait). Neverland was evaluated for the slot but is a lending protocol (Aave V3 fork), not staking — noted as a future lending plugin instead.

decisionTrust verified addresses, env-overridable

For each protocol I shipped the canonical mainnet addresses as defaults (sourced from monad-crypto/protocols), with env vars to override. Different model from Uniswap (which fail-loud-on-missing) because these protocols have stable canonical singletons that don't churn. Testnet defaults remain null — set per-protocol env vars if you have testnet deployments.

decisionLiquid-staking plugins share shape but not code

Kintsu and FastLane are both MON → LST flows but with different unstake mechanics. Kintsu uses ERC-7535's requestUnlock(shares) → redeem(unlockIndex, receiver) with batched processing. FastLane's shMONAD is plain ERC-4626 with a synchronous redeem(shares, receiver, owner) — no queue, no epoch. The signatures differ enough that abstracting them into one plugin would muddy the boundaries — kept separate. Their grant integration and approval flow code paths are identical (both call tryExecuteViaGrant, both fall through to store.create on miss), which is the property that mattered.

decisionMorpho takes MarketParams inline, computes id client-side

Morpho Blue identifies markets by id = keccak256(abi.encode(MarketParams)). Two API options: (a) take a market id and look up MarketParams server-side, (b) take MarketParams inline and compute id locally. Picked (b) because: it's stateless (no on-startup market fetch), the agent already has MarketParams from any Morpho discovery flow, and the failure mode is honest ("wrong MarketParams → wrong market" vs. "stale cached id → wrong market"). marketId() in plugins/morpho/market.ts is the one place that does the keccak.

decisionKuru orders use raw integers, not human numbers

Kuru's addBuyOrder(uint32 price, uint96 size) uses per-market price + size precision exposed by getMarketParams(). Two ways to handle this from an MCP: (a) auto-fetch market params and convert decimal inputs, (b) require callers to pass raw integers and provide kuru_market_params as the converter. Picked (b) — auto-conversion would hide a critical safety property (the agent should KNOW the precision before placing a 100-MON order). Documented the constraint in the tool description.

decisionPlugin network gating happens at registration time

The four new plugins declare networks: ["mainnet"]. registerPlugins skips them at boot when defaultNetwork === "testnet" and logs a warning. This avoids exposing tools that will fail with "not configured" errors on every call. Tradeoff: tools can't be invoked with network: "mainnet" on a testnet-default server because they're not registered at all. If you need both at once, set the server to mainnet and pass network: "testnet" where supported.

tradeoffHealth factors computed off-chain

Morpho's position() view returns shares + collateral. The actual health factor requires the oracle price for the collateral and the LLTV — neither cheap to fetch in a single call. Shipped raw fields; let the agent (or a future helper) compute health from the snapshot. Avoids the silent-staleness problem of cached per-tool health values.

openActive Morpho markets discovery

Morpho's active market set churns weekly. Hardcoding sample markets would be wrong by the time the next person reads this. The intended flow is "agent queries Morpho's GraphQL at api.morpho.org/graphql with chainId: 143, gets current MarketParams, passes them to morpho_supply". A future morpho_list_markets tool that does that GraphQL query server-side would close the loop — worth adding when the Monad market set stabilizes.

openKuru order book reading

getL2Book() returns packed bytes that need protocol-specific decoding. Shipped bestBidAsk() as the cheap read; full L2 decode is on the roadmap. For most agent use cases, best bid/ask + market params is enough to size an order.

openKintsu / FastLane share price → APY

Neither protocol exposes APY on-chain. Computing it requires sampling convertToAssets(1e18) at two timestamps and annualizing the delta. We could either (a) cache snapshots server-side, (b) read the protocols' off-chain analytics APIs, or (c) make the agent do it. For v1 the position tools expose the snapshot share price — agents can chain two calls themselves if needed.

7. Phase 2 additions

decisionSession-key grants at the MCP layer, not the wallet layer

The clean way to do delegated permissions on Privy is to create a wallet policy (Privy policies() API supports EthereumTransactionCondition + spend-limit aggregations). I chose to track grants at the MCP server layer instead. Reasoning:

  • One grant store, swap to Postgres/Redis later — same interface.
  • Can pre-flight coverage check before calling Privy at all (avoids spending API quota on calls we'll reject).
  • Same grant shape works with WalletConnect / other wallet providers later.
  • Wallet-layer policies remain available as defense-in-depth (mirror the grant as a Privy policy on activation — wired in a follow-up).

Tradeoff: trust the MCP server's authoritative view of the cap. The wallet itself isn't constrained, so an attacker with server access could bypass the cap by calling Privy directly. The fix is to mirror the grant as a Privy policy — write a future commit.

decisionNative-MON cap only in v1

Grant spendCapWei only tracks native-MON spend. ERC-20 token amounts aren't deducted (would need to decode calldata + apply token-by-token caps). For v1 the workaround is to restrict per-token access via allowed_targets — list only the ERC-20 contracts you trust the agent to interact with. Per-token spend caps are a v2 surface.

decisionGrant activation reuses the stored-request approval flow

Instead of a separate "approve-grant" page, the grant_session_key tool creates a StoredRequest with pluginContext.kind === "grant_activation". The submit endpoint recognizes the sentinel and calls grants.activate instead of submitting an on-chain tx. One page, two purposes — fewer moving parts.

decisionAtomic charge-then-send with refund on failure

Inside tryExecuteViaGrant: charge the cap first, then call Privy. If Privy submission fails we call refundSpend to roll back. Charge-first avoids a race window where two concurrent agent calls both pass coverage check then both submit. Briefly the cap reads over-charged between charge and refund — acceptable.

deviationUser access tokens not minted server-side

Privy's node SDK doesn't expose a "mint user JWT" helper for testing. For the e2e script we synthesize an AuthInfo directly (bypassing the OAuth layer) and call runTool in-process. Tests the same code paths the HTTP route does, just without the bearer-verification step. The HTTP/OAuth layer was already smoke-tested separately.

openMirror grants as Privy policies

Defense-in-depth: when activating a grant, also create a Privy policy that mirrors the cap and call walletsService.update to attach it. On revoke, detach. Means a compromised MCP server can't bypass the user's intent.

openGrant + simulation

Grant coverage today is decided pre-flight. We could go further: simulate the call via Tenderly-equivalent, infer the actual asset deltas, and apply per-token caps based on what the simulation reports. Avoids the "did we just drain the wallet" failure mode.

8. OAuth 2.1 bridge to Privy (hosted write flow)

To let a non-coder connect the hosted URL in Claude Desktop / ChatGPT and actually send transactions, the server now acts as a small OAuth 2.1 authorization server in front of Privy login. New surface: POST /oauth/register, GET /authorize, POST /authorize/consent, POST /token (in src/auth/oauth-routes.ts + oauth-store.ts + login-page.ts).

decisionPass-through tokens, not our own JWTs

The bearer token we issue at /token is the user's Privy access token, verbatim. The existing privyTokenVerifier already validates Privy JWTs via JWKS, so wrapping them in our own JWT would add a second signing identity and key-management burden for zero gain. Scopes are assigned server-side at verification time, so they don't need to live in the token.

decisionSelf-describing signed client_id for Dynamic Client Registration

Rather than persist a client table, client_id is base64url(JSON).hmac encoding the registered redirect URIs (same HMAC trick as the approval token). Verifying the signature re-derives the redirect allowlist — no DB lookup, survives restarts and multiple machines. Fixes the original 404 at /oauth/register that broke connector login entirely.

tradeoffAuthorization codes are in-process, not persisted

Codes must be one-shot, which a stateless signed token can't guarantee (no way to invalidate after use). So codes live in an in-memory TTL map (AuthCodeStore), deleted on redemption — true single-use, 2-minute TTL. Cost: a code minted on one machine can't be redeemed on another, and codes don't survive a restart. Acceptable because the hosted endpoint runs min_machines_running=1 and the authorize→token gap is seconds; on a miss the user just re-runs login (usually silent if their Privy session is warm).

decisionPKCE S256 required; redirect_uri validated before any redirect

/authorize verifies client_id and that redirect_uri is in its registration before ever issuing a redirect, so we can't be turned into an open redirector. Protocol errors after that point bounce back to the validated URI with error/state. Only code_challenge_method=S256 is accepted. DCR rejects redirect URIs that aren't https or http-loopback.

deviationNo refresh_token grant in v1

Privy session refresh is a browser concern (the SDK holds the refresh token), not something the server SDK exposes cleanly. So we advertise only authorization_code. When the Privy access token expires (~1h), the MCP client re-runs /authorize; because the user's Privy session cookie persists on our origin, that re-auth is typically silent. expires_in is derived from the token's own exp claim so clients refresh on time.

openBrowser login page is unverified without live Privy creds

The login page (login-page.ts) loads React + @privy-io/react-auth as browser-native ESM from esm.sh (no build step, React.createElement so no in-browser Babel). Everything around it is unit-tested (10 tests, full register→authorize→consent→token flow over a live ephemeral server) and smoke-tested against a running server. But the actual Privy login modal can only be exercised with a real Privy appId whose "Allowed origins" includes the server's publicBaseUrl — i.e. one live deploy. Two specific risks to confirm on that first run: (1) esm.sh reliably serves the (heavy) react-auth bundle; (2) getAccessToken() returns a token the server-side verifier accepts. If esm.sh proves flaky, the fallback is a tiny Vite-built static asset.

decisionSigning secret reuses MONAD_MCP_APPROVAL_SECRET

Client-id signing uses the existing approval secret. If unset, the server logs a warning and generates an ephemeral one at boot — the flow still works, but registered clients invalidate on restart, so a stable secret is recommended for any real deploy.

8b. Client-side signing on the approval page (2026-06-04)

Added after a hosted-deploy incident: a user's "Approve & sign" failed with PRIVY_AUTHORIZATION_PRIVATE_KEY is not set. Root cause was a missing server signing key, but fixing that surfaced the deeper issue below.

decisionThe approval page now signs in the browser with the user's own wallet

The page (page.ts) previously only POSTed to /submit, which signs server-side via the Privy node SDK and our P-256 key quorum. That requires the user's embedded wallet to carry our quorum as an additional_signer — which is only attached by server-side createUserWithWallet. A wallet created by browser Privy login (the OAuth connector path) has no such signer, so server signing can never work for it: those wallets are "stranded." The page's own header comment had long claimed it signed client-side, but the code never did. It does now: renderClientMode() loads @privy-io/react-auth from esm.sh (mirroring login-page.ts), authenticates the user, finds the embedded wallet matching the request's From address, calls wallet.switchChain() + getEthereumProvider() and broadcasts via standard eth_sendTransaction — the user's wallet pays gas and holds the key. No server signer needed; the stranded-wallet failure class disappears.

decisionNew /confirm endpoint records client-signed txs, with an on-chain integrity gate

After broadcasting in-browser, the page POSTs the resulting hash to POST /api/stored-requests/:id/confirm. The server never signs; it (1) authenticates the caller (shared authorizeFor — Privy bearer or the per-request approval token, same as /submit), (2) checks ownership, and (3) runs assertOnChainMatch: fetches the tx by hash and asserts from/to/value/calldata match the approved request before recording it. A found-but-different tx is rejected (409); a not-yet-indexed tx is accepted (propagation lag — the caller is already a proven owner). 9 new route tests run against a real ephemeral express server.

tradeoffBoth signing paths kept; mode chosen per request

The server-submit path is preserved for grant-activation requests, which have no browser transaction to sign (they flip a server-side grant and mirror a Privy policy). approvalPage sets signingMode: "server" for pluginContext.kind === "grant_activation" and "client" otherwise; /confirm refuses grant activations (400) and /submit still handles them. This keeps every existing flow working while making client-side signing the default for real transfers/contract calls.

openThe Privy web-SDK signing call is unverified against a live wallet

Same caveat as the login page: the esm.sh react-auth import, switchChain to a custom Monad chain, and eth_sendTransaction through the embedded-wallet provider can only be exercised end-to-end with a real logged-in wallet on an allowed origin. The server side (/confirm + integrity check) is fully unit-tested; the browser side needs one live round-trip to confirm. Server-provisioned wallets (proven this session via a real broadcast that failed only on insufficient balance) remain a working fallback through /submit.

9. Read-public / write-gated split (optional bearer auth)

When Privy was configured, the entire POST /mcp endpoint was wrapped in the SDK's requireBearerAuth, so every call — including read-only tools and even initialize/tools/list — got a 401 without a token. On the live hosted endpoint (which has Privy secrets) this silently broke the advertised "paste the URL, read with zero auth" flow: a client that can't do interactive OAuth (headless loaders, some connectors) enumerated zero tools and reported the server as "unreachable." The fix splits read from write at the transport edge.

decisionEndpoint auth is now optional; writes self-gate per-tool

New middleware optionalBearerAuth (src/auth/optional-bearer.ts) replaces requireBearerAuth on /mcp by default. No Authorization header → the request passes through anonymously and runs read tools; the existing per-tool gate in runTool (def.kind === "write" && !auth → AuthRequiredError) already blocks writes, so no token is ever needed to read. A valid Bearer token is verified (same Privy verifier) and attached as req.auth, which the Streamable-HTTP transport forwards as extra.authInfo to unlock writes. The write-gating logic didn't change — only where the read/write boundary is enforced moved from the endpoint to the tool.

decisionA malformed/expired token is a hard 401, not a silent downgrade

If a client bothers to send a bearer, it meant to authenticate, so a bad or expired one returns 401 with a spec-compliant WWW-Authenticate challenge (pointing at the resource-metadata URL) rather than quietly falling back to anonymous read-only. Only a genuinely absent header is treated as anonymous. This mirrors the SDK's requireBearerAuth behavior for the present-but-invalid case, including the same expiry checks.

tradeoffWrites fail in-band, so anonymous clients aren't auto-prompted to log in

Because anonymous reads never receive a 401, a spec-compliant client won't automatically trigger its OAuth flow — a write instead returns an in-band auth_required tool result telling the user to sign in. That's the right call for the primary use case (frictionless reads) and the OAuth discovery metadata is still served, so a client that wants write access can authenticate proactively. The alternative — 401-ing writes at the transport to force the OAuth handshake — would require routing per-tool kind before the JSON-RPC body is dispatched, which the stateless transport doesn't expose cleanly.

decisionMONAD_MCP_REQUIRE_AUTH escape hatch preserves strict mode

Operators who want the old "token for everything" posture set MONAD_MCP_REQUIRE_AUTH=true, which swaps optionalBearerAuth back for the SDK's strict requireBearerAuth. Parsed with an explicit allow-list (1/true/yes/on) rather than z.coerce.boolean(), which would coerce the string "false" to true (any non-empty string is truthy) — a footgun covered by a regression test.
